# 从 0 到 1：我用 Django 做了一个真的能交易的校园二手平台

> **闲小集** · 一个面向学生的校园二手交易集市
> 技术栈：Python 3.13 / Django 5.2.19 / SQLite / Bootstrap 5 / Pillow
> 代码：主要文件约 5,300 行 · 9 张数据表 · 15 个页面模板
> 源码：https://github.com/songxufeng-Seanfin/campus-secondhand-market
> 早期演示地址（后面加的信用体系、手机端 Tab 和 PWA 以仓库版本为准）：https://xianxiaoji-market.app.workbuddy.host/?sharecode=LCIVOQTNSK

---

## 写在前面

校园里卖闲置，大多靠群聊刷屏：一本书的照片发出来，三分钟就被新消息顶没了；想找辆自行车得翻半天聊天记录；交易全靠「你信我我也信你」。

所以我想做的不是又一个「商品展示页」，而是一个**能走完整条链路**的小集市：从发布、浏览、议价，到下单、完成交易、互相评价。这篇文章记录它是怎么一层层搭起来的，也记录几个把我卡了很久的坑。

写得多了才发现，十几个功能其实是同一套骨架重复搭了很多遍，这篇就按这个顺序往下记。

## 一、先看成品：四块功能

我没有按「页面」来规划，而是按「人在集市里干什么」分成四块：

| 分块 | 能做什么 |
|---|---|
| **逛** | 首页商品流、关键词搜索、分类筛选、上滑自动加载、商品详情（浏览量 / 同类推荐 / 留言板）、一键收藏 |
| **发** | 注册登录、发布闲置（图片、定价、成色、交易地点、包邮设置）、编辑下架、我的闲置 |
| **聊与买** | 「我想要」「直接购买」直达一对一私聊；会话顶部钉着商品横幅和「立即购买」；下单可选**面对面**或**线上**，填地址、算运费、模拟支付；订单状态流转 |
| **信用** | 交易完成后买卖双方互评 1～5 星；公开主页展示好评率、均分、成交数、收到的评价 |

外面再套两层壳：手机端底部 Tab 栏，以及「添加到主屏幕」后像 App 一样全屏打开（PWA）。

## 二、技术选型：为什么是 Django

先说一个我后来才想明白的区别：**工具是你叫它干活，框架是它来叫你。**

Pillow（Python 的图片处理库）是工具——我说「把这张图裁成 1200×900」，它裁完就完事。Django 是**框架**：网址命中了，它反过来去调用我写的那个函数。流程、登录、后台、防伪造提交、数据库读写，全是它自带的；我只往固定格子里填「商品 / 订单 / 评价」这些房间。

这带来的直接好处是：**依赖只有两个**。

```
Django==5.2.*
Pillow
```

没有 npm、没有 webpack、没有前端构建。Bootstrap 5 和图标库从 CDN（内容分发网络，别人托管好的公共文件）直接引用，样式写在模板里。对一个练手项目来说，这个简单度非常关键——我不用先学会五套工具链，才能看到第一个页面。

Django 用的是 **MVT** 分层，说白了就是把事情拆成三份：

- **M（Model 模型）**：数据长什么样、存在哪 → `models.py`
- **V（View 视图）**：收到请求后干什么活 → `views.py`
- **T（Template 模板）**：把数据摆成页面 → `templates/*.html`

数据库选了 **SQLite**：整个库就是一个 `db.sqlite3` 文件，零配置、能直接拷走。对本地开发和演示足够，后期换 MySQL / PostgreSQL 也只是改 `settings.py` 里的一个配置。

## 三、整个系统的骨架：一次点击走一圈

这是我觉得最值钱的一张图，因为**所有功能都是这一圈在反复跑**：

```
你点一下按钮
   ↓  浏览器发出「请求」：网址 + 表单内容 + 登录小票
服务器照着网址跑一圈
   安检 → 路由分诊 → 视图干活 → 读写数据库 → 模板拼页面
   ↑  回送「响应」：一份 HTML
浏览器把 HTML 画成页面
```

页面不会自己变。收藏数变了、来了条新消息，都是又跑了一圈（或由 JavaScript 悄悄再跑一小圈）。而且一次刷新其实**不止一圈**：先取页面，页面里的 CSS、脚本、商品图片又各自发请求去取。

把 Django 内部那一圈拆开，是六站：

| 站 | 干什么 | 谁提供的 |
|---|---|---|
| 1 中间件 | 认出登录的人、验表单凭证 | Django 自带 |
| 2 路由 | 这个网址交给哪个函数 | 我写一张表 |
| 3 视图 | 查什么数据、改成什么 | 我写 |
| 4 模型 / 数据库 | 把 Python 翻成数据库指令 | Django 翻译，表结构我定 |
| 5 模板 | 把数据排成 HTML | 我写 |
| 6 响应 | 送回浏览器 | Django 自带 |

**六站里真正属于我写的只有中间四格，而且都是「填内容」，不是「造流程」。** 想通这一点，项目一下子从「五千行天书」变成了「四格填空」。

顺带，那些曾经看不懂的三位数报错，也终于有位置了：

| 代号 | 意思 | 我这次撞上的具体原因 |
|---|---|---|
| **404** | 找不着路 | 线上数据被发布覆盖，那个商品 id 不存在了 |
| **405** | 路找到了，方式不对 | `rate` 被通配路由吞掉，落到只收 POST 的路上 |
| **403** | 门卫不认凭证 | 公网域名没进受信任列表，手机登录被拦 |
| **500** | 里面某段代码出错 | 没真出现过，全站巡检专门查它 |

记法：**404 找不着路、405 方式不对、403 不让进、500 里面出错**。要注意「代号的定义」和「那次为什么撞上」是两回事——「被覆盖」不是 404 的定义，只是那一次让路消失的原因。

## 四、数据怎么设计：九张表撑起整个集市

想清楚「存什么」，功能就成型了一半。九张表：用户、分类、商品、订单、收藏、商品留言、私聊会话、会话消息、交易评价。

串起来看：一个用户发布多件商品，另一个用户对某件商品发起会话，聊完下一笔订单，完成后双方各留一条评价。

### 订单是个状态机

**状态机**就是规定「哪些状态能变成哪些状态」：

```
pending 待确认 ──卖家确认──→ accepted 待收货 ──确认收货──→ completed 已完成
    │                            │
    ├──卖家拒绝──→ rejected      └──买家取消──→ cancelled
    └──买家取消──→ cancelled
```

只有走到 `completed` 才能互评。完成那一刻还会做两件联动：商品标记「已售出」，同一件商品其他进行中的订单自动关闭——不然一件东西会被卖给两个人。

### 四个唯一约束

**约束**是数据库层的最后一道兜底，比在代码里写 `if` 可靠：连点两次、网络重试、两个请求同时到达，数据库也只让存一条。

| 约束 | 防什么 |
|---|---|
| `(用户, 商品)` 收藏唯一 | 重复收藏 |
| `(商品, 买家)` 会话唯一 | 同一件商品被拆成好几条聊天 |
| `(商品, 买家)` **在订单进行中时**唯一 | 重复下单；但订单结束后允许再买 |
| `(订单, 评价人)` 唯一 | 一笔订单重复评价 |

第三条是**条件唯一约束**（只在满足条件的行上生效），写起来是这样：

```python
models.UniqueConstraint(
    fields=["product", "buyer"],
    condition=Q(status__in=["pending", "accepted"]),
    name="uniq_active_order_per_buyer_product",
)
```

另外两个我挺喜欢的小决策：

- **订单存成交价快照**，不实时读商品价——卖家后来改价，不影响已成交的订单；
- **信用分不存用户表**，用 `aggregate(Count, Avg)` 实时算——每笔成交最多 2 条评价，数据量极小，实时算反而避免了「两处数据对不上」。

## 五、几个让我真正理解 Web 的实现

### 1）收藏：最短的一条完整闭环

它是全项目最短、但五脏俱全的功能，五站全走一遍：

```python
# goods/views.py
favorite, created = Favorite.objects.get_or_create(
    user=request.user, product=product
)
if created:
    messages.success(request, "已加入收藏")
else:
    favorite.delete()          # 一个接口同时管「加」和「删」
return redirect(...)           # 提交后重定向，防刷新重复提交
```

- 表单用 `method="post"` 而不是链接：因为点一下会改数据库，链接会被浏览器预加载 / 刷新 / 爬虫误触发；
- `{% csrf_token %}` 藏一张一次性凭证，确认「这请求真是我自己的页面发的」；
- 用户身份取 `request.user`（服务器从登录态认出来的人），**不信任前端传的用户名**，否则谁都能替别人收藏；
- `redirect` 而不是直接渲染（这个套路叫 **PRG**），按 F5 不会重复提交。

其他十几个功能，都是这条链路换了张表和一段判断。

### 2）上滑自动加载

首页每页 6 件。前端用浏览器自带的 `IntersectionObserver`（元素进入视野就通知）盯住列表底部的哨兵，提前 240px 触发；请求时带一个 `X-Requested-With` 头，后端就**只返回商品卡片片段**，不重复传整页；再用两个自定义响应头 `X-Has-Next` / `X-Next-Page` 告诉前端还有没有下一页。

老浏览器退化成滚动监听，加载失败还能回退到手动翻页——**降级方案**比主方案更容易被忽略，但它决定了用户会不会卡死在空白页。

### 3）私聊：轮询就够了

详情页「我想要」和「直接购买」进的是**同一个会话**（靠唯一约束保证）。聊天页是微信式双栏：左边会话列表，右边对话窗，顶部钉着商品横幅和橙色「立即购买」。

发消息用 `fetch` 局部插入气泡，不整页刷新；每 3 秒带「最后一条消息 ID」去问一次有没有新消息，只拉增量。这叫**轮询（Polling）**，不是 WebSocket，但对校园集市这个量级完全够用，实现也简单得多。

未读红点没有单独做通知表：`ChatMessage` 上有个 `is_read` 字段，再用**上下文处理器**（自动塞给所有页面的变量）统一算一次，导航栏和手机 Tab 栏就都有了。

### 4）下单双模式与服务端校验

面对面交易 = 校内自提，不填地址不收运费；线上交易 = 填收货人 / 电话 / 地址，按卖家发布时设的「包邮 / 不包邮（¥8）」算运费，可立即模拟支付。

下单动作包在 `transaction.atomic()`（**事务**：几步操作要么全成功要么全回滚）里，撞上唯一约束就捕获 `IntegrityError` 并提示「你已经下过单了」。订单状态流转同理，所有动作都按「身份 + 当前状态」双重判断——**前端藏按钮只是体验，不是安全边界**，服务端必须自己再验一遍。

## 六、最痛的一个坑：朋友发布的商品消失了

这个必须单独写一节。

朋友在线上注册、发了两件商品，我更新了一版代码重新发布，商品没了。

**根因不是代码写错，是「东西放在哪」错了**：`db.sqlite3` 和用户上传的 `media/` 原本都放在项目目录里，而发布是「把整个源码目录覆盖上传」。于是每次更新代码，随包附带的旧数据库就把真实数据冲掉了。代码可以反复覆盖，**数据不可以**。

修法是把数据和代码分开：

```python
# config/settings.py
DATA_DIR = Path(os.environ.get("XJ_DATA_DIR") or BASE_DIR)
DATABASES["default"]["NAME"] = DATA_DIR / "db.sqlite3"
MEDIA_ROOT = DATA_DIR / "media"
```

本地不设 `XJ_DATA_DIR` 时，数据仍在项目目录，开发体验不变；线上启动脚本把它指向 `~/.xianxiaoji`（发布目录之外），**源码目录怎么覆盖都碰不到数据**。修完我模拟连续发布两次验证，账号和商品都还在。

旧数据没能恢复——被覆盖后没有备份。这是整个项目代价最大的一课，也是我现在做任何项目都会先问的一句：**这个东西会被重新部署冲掉吗？**

顺带一提，线上启动脚本 `start.py` 也踩了个小坑：部署平台只注入一个 `PORT` 环境变量，而启动命令里的 `$PORT` 不一定会被 shell 展开，所以最后用 Python 直接 `os.environ.get("PORT")` 读，再启服务。

## 七、另外三个坑，每个都是一节课

**手机登录 403**：电脑正常、手机不行。因为站点在反向代理后面，浏览器带来的 `Origin` 是公网域名，没进 `CSRF_TRUSTED_ORIGINS`，Django 的门卫不认那张凭证。加上受信任来源后就好了，我还把它改成可配置的环境变量，换域名不用改代码。

**点商品 404**：和上面那个数据丢失是同一根。除了根治存储位置，详情页也加了兜底——商品不存在时提示后跳回首页，而不是甩一张错误页给从旧链接点进来的用户。

**评价页 405**：路由表里 `orders/<id>/<str:action>/` 写在前面，`rate` 被当成 action 吞掉，落到只收 POST 的视图上，GET 就被拒。Django 路由**从上往下匹配，第一条命中就停**，把具体路由挪到通配路由前面就好了（代码里留了注释，防止以后再犯）。

还有一个**预防性设计**值得记：做 PWA 时，Service Worker（浏览器后台的代理脚本）**只缓存站内图片，绝不缓存 HTML**。因为页面里含一次性 CSRF 凭证，缓存旧页面会让凭证过期复用，等于把 403 那个坑再踩一遍。把前面的教训提前堵住，比事后修舒服得多。

最后是个假警报：用无头浏览器验证手机端时看到「横向溢出」，紧张了半天，结果是**无头 Edge 最小窗宽 500px** 造成的假象，不是 CSS 问题。教训：先确认测量工具本身的限制，再怀疑代码。

## 八、手机端：一条栏和一个图标

顶部导航在手机上很挤，常用的四个入口要一步点到。于是加了贴底 Tab 栏「首页 / 发布 / 消息 / 我的」，发布居中凸起，当前页高亮，消息带未读红点。

实现全在 `base.html` 一份文件里：用 **CSS 媒体查询**（一句「屏幕窄于 767px 才生效」的规则）控制显示，`env(safe-area-inset-bottom)` 适配全面屏下巴，聊天页因为有输入条就自动隐藏。因为所有页面都继承这份外壳，**改一处，十几页全都有了，一行 Python 都没动**。

PWA 那部分则是三个根路径文件：`manifest.webmanifest`（应用清单，声明全屏启动和图标）、`sw.js`（缓存脚本）、三档品牌图标（Pillow 画的纸箱笑脸）。挂到根路径是为了让 Service Worker 的作用域覆盖整个站点。

## 九、怎么确认它「真的能用」

我没有只靠肉眼看页面。收尾时做了两类检查：

1. **全站巡检**：列出 21 个地址，用 Django 的测试客户端（`django.test.Client`，不启服务器也能模拟浏览器发请求）在**已登录 / 未登录两种状态各跑一遍**，共 42 次请求，确认没有 500、图标不缺、PWA 标签齐全；
2. **写操作冒烟测试**：越权改别人商品应被 404 拦、收藏加 / 删、留言写入、发私聊消息、完整走一遍「下单 → 卖家确认 → 完成 → 评价」。测完把造出来的临时订单、留言、消息全清掉，不留脏数据。

外加桌面 / 手机两种宽度的截图核对布局。所谓「测试」，说白了就是：**模拟点一下按钮，然后检查结果对不对**——名字唬人，内容很朴素。

## 十、回头看：这个项目到底给了我什么

功能清单可以罗列很长，但真正留下的是三样东西。

最明显的是看东西的方式变了。 以前看到一个页面是一整块；现在会自动拆：谁画的（HTML/CSS）、网址交给谁（路由）、干了什么活（视图）、存在哪（模型 / 数据库）。拆开之后，报错不再是天书，而是「卡在第几站」。

另一个是「防」比「做」更花时间。 收藏按钮真正的核心只有 5 行，但 POST 而非 GET、CSRF 凭证、`request.user`、唯一约束、PRG、相对跳转校验，全是围着这 5 行加的。写代码几分钟，验证和兜底是它的好几倍。

还有判断需求这件事。 从「私聊要像微信那样是独立界面、还要能和不同商品不同买家聊」到「会话顶部要有商品横幅和直接购买」，这些不是语法问题，是把一个模糊的想法拆成表、路由、视图、模板四格的能力。

下一步打算做的：多图上传、个人资料编辑、把 3 秒轮询换成 WebSocket 实时推送，以及真正上生产（gunicorn + Nginx + PostgreSQL、关掉 DEBUG）。每一条都能独立做，不影响现有功能。

pip install -r requirements.txt
python manage.py migrate
python manage.py seed_demo
python manage.py runserver
