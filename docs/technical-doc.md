## 1. 项目概览

**这一层讲什么**：这个项目解决什么问题、最终做成了什么、用了哪些技术。

### 1.1 解决什么问题

校园里买卖二手书、自行车、耳机，通常靠微信群刷屏：信息一闪就过、没法按分类找、也不好判断对方靠不靠谱。「闲小集」把它做成一个**有商品列表、有详情页、能私聊议价、能下单、能互评**的小集市，全部围绕「校内自提、学生之间交易」这个场景。

## 2. 第一层：从屏幕到服务器

**这一层讲什么**：按一次刷新，背后发生了什么；那些看不懂的三位数报错，到底卡在哪一站。
**会碰到的新词**：请求、响应、状态码、客户端 / 服务端、CDN。

### 2.1 一次点击 = 跑一圈

整个网站所有变化，都是同一圈在反复跑：

```
你点一下 / 按 F5
    ↓  浏览器发出「请求」（带上网址、填的表单、登录小票）
服务器（一台一直开着、跑着我们代码的电脑）
    ↓  照着网址跑一圈：安检 → 找路 → 干活 → 拼页面
    ↑  回送「响应」：一份 HTML 文本
浏览器把 HTML 画成页面
```

**关键认知**：页面不会自己变。收藏数变了、来了条新消息，都是又跑了一圈（或由 JavaScript 悄悄再跑一小圈）。

**一次刷新其实不止一圈**：先取页面这一圈；页面里的 CSS、JS、商品图片又各自发请求去取。你只按了一下，背后是好几圈。

### 2.2 网址说了两件事

```
https://xianxiaoji-market.app.workbuddy.host/product/8/
└──────────── 找哪台服务器 ────────────┘└─ 找哪条路 ─┘
```

前半段由域名解析找到服务器；后半段 `/product/8/` 交给服务器里的**路由表**去分诊。这里的「路由」是网站内部的一张网址分诊表，**不是家里那个路由器设备**。

### 2.3 状态码：报错终于有位置了

| 代号 | 定义（永远不变） | 本项目里那次的具体原因 |
|---|---|---|
| **404** | 这条路没找到 | 线上数据被发布覆盖，商品 id 不存在了 |
| **405** | 路找到了，但**请求方式不对** | `rate` 被通配路由吞掉，落到只收 POST 的路上，GET 被拒 |
| **403** | 门卫不认凭证 | 公网域名没进受信任列表，手机登录带的一次性凭证被拦 |
| **500** | 里面某段代码执行出错 | 项目里没真正出现过；全站巡检就是专门查它 |

> 记法：**404 找不着路、405 方式不对、403 不让进、500 里面出错**。
> 容易混的一点：「定义」和「那次为什么撞上」是两回事。「被覆盖」不是 404 的定义，只是那一次让路消失的原因；换任何一个不存在的商品，一样是 404。

## 3. 第二层：Django 收到请求之后的流水线

**这一层讲什么**：把上一章那「一圈」拆开，看框架内部怎么分活、怎么记住你是谁。
**会碰到的新词**：框架、MVT、中间件、Session / Cookie、CSRF、ORM、`request.user`。

### 3.1 「框架」和「工具」的区别

**Django 不是我们写的**，是别人已经盖好水电的楼。登录注册、后台管理、门卫、数据库读写这些通用活它自带，我们只往里填「商品 / 订单 / 评价」这些房间。

有个反转值得记：Pillow 那种**工具**是你叫它干活（说「裁图」，它就裁）；Django 这种**框架**反过来，**是它来叫你**——网址命中了，它跑去调我们写的那个函数。流程是框架定好的，我们只往固定格子里填内容。所以叫「框架」不叫「工具包」。

Django 用的是 **MVT（模型 - 模板 - 视图）** 分层，和常见的 MVC 是同一类思想，只是名字不同：

| MVT | 白话 | 文件 |
|---|---|---|
| **M**odel 模型 | 数据长什么样、存在哪 | `models.py` |
| **V**iew 视图 | 收到请求后干什么活 | `views.py` |
| **T**emplate 模板 | 把数据摆成页面 | `templates/*.html` |

### 3.2 六站流水线

| 站 | 名称 | 干什么 | 谁提供的 |
|---|---|---|---|
| 1 | **中间件**（Middleware，请求进门先过的几道固定安检） | 认出登录的人、验表单凭证 | Django 自带，顺序写在 `settings.py:41-49` |
| 2 | **路由**（URLconf，网址分诊表） | 这个网址交给哪个函数 | 我们写一张表 `goods/urls.py` |
| 3 | **视图**（View） | 查什么数据、改成什么 | 我们写 `goods/views.py` |
| 4 | **模型 / ORM → 数据库** | 把 Python 翻成数据库指令，读写 `db.sqlite3` | Django 翻译，表结构我们定 |
| 5 | **模板**（Template） | 把数据排成 HTML | 我们写 `templates/*.html` |
| 6 | **响应**（Response） | HTML 送回浏览器 | Django 自带 |

看这张表能发现一件事：**六格里真正属于我们写的只有中间四格，而且都是「填内容」，不是「造流程」**。这就是「项目里自己的代码比看上去少得多」的原因。

### 3.3 四个关键词的白话版

- **Session / Cookie（会话 / 小票）**：登录成功后服务器给浏览器一张小票，之后每次请求自动带着；服务器凭小票认出你是谁。这个被认出来的人，在代码里就叫 **`request.user`**。所以收藏按钮不用写用户名，也替不了别人收藏（`goods/views.py:541`）。
- **CSRF（跨站请求伪造防护）**：安检里的那个门卫。每个表单藏一张一次性凭证（`{% csrf_token %}`），确认「这请求真是我自己的页面发出的」。手机登录 403 那次，就是这张凭证和线上域名对不上。
- **ORM（对象关系映射）**：模型那一站的翻译官。我们只写「取这个用户收藏的商品」这样的 Python，不用手写 SQL（数据库查询语言），Django 负责翻译。
- **上下文处理器**（Context Processor）：网站自动塞给**所有**页面的现成信息。导航栏未读红点就是这么来的——写在 `goods/context_processors.py`，在 `settings.py:64` 注册一次，首页、详情页全都自动有。

### 3.4 顺带解释那次最痛的事

朋友发布的商品不见了，**不是代码写错，是「东西放在哪」的问题**：数据库文件跟着项目目录走，发布时整个目录被覆盖，它就一起没了。后来把数据挪到发布目录之外（第 8 章），就再没丢过。这件事落在流水线的**第 4 站**。

## 4. 第三层：项目骨架与文件职责

**这一层讲什么**：代码放在哪些文件里、各自管什么、为什么改了模型还要「迁移」。
**会碰到的新词**：应用（App）、迁移（Migration）、管理命令、模板继承。

### 4.1 目录树


### 4.2 三个「应用」

Django 把一个大项目拆成若干 **App（应用，可复用的功能模块）**。本项目两个：

- `accounts`：只管「谁在用」——注册、登录、个人中心。
- `goods`：管「集市里发生的一切」——商品、订单、收藏、留言、私聊、评价。

登录登出甚至没自己写视图，直接复用 Django 内置的 `LoginView` / `LogoutView`（`accounts/urls.py:9-14`），这就是「框架自带水电」的意思。

### 4.3 迁移是什么

改了 `models.py`（比如给订单加「运费」字段），数据库不会自己变。**迁移（Migration）** 就是一份「数据库结构变更说明书」：

```bash
python manage.py makemigrations goods   # 对比模型与现有结构，生成一份变更说明书
python manage.py migrate               # 按说明书真的去改数据库
```

项目里 `goods/migrations/` 有四份：

| 文件 | 对应哪次功能 |
|---|---|
| `0001_initial.py` | 分类、商品表 |
| `0002_...py` | 订单、收藏、商品留言 |
| `0003_...py` | 双模式交易（地址 / 运费 / 支付状态） |
| `0004_rating.py` | 交易评价 |

**为什么要提交这些文件？** 因为队友拉下代码后跑一次 `migrate`，就能得到一模一样的表结构；`start.py` 在线上启动时也是这么做的。

### 4.4 模板继承

`base.html` 是**所有页面共用的外壳**：导航栏、设计变量、页脚、手机 Tab 栏、PWA 标签、Bootstrap 引入，全写在这一份里。其他模板第一行都是 `{% extends "base.html" %}`，只填中间那块内容。所以「加一条手机底部栏」只改一个文件，全站十几页就都有了。

## 5. 第四层：数据层设计

**会碰到的新词**：表 / 字段 / 主键 / 外键、约束、索引、事务、状态机、聚合。

### 5.1 九张表与关系

| 表 | 白话：存什么 | 关键外键 |
|---|---|---|
| `accounts_user` | 用户（用户名、密码哈希、手机号、头像） | — |

| `goods_order` | 订单（成交价快照、交易方式、收货信息、运费、支付状态、状态） | → 商品、→ 买家、→ 卖家 |

| `goods_chatmessage` | 会话里的每条消息（含已读标记） | → 会话、→ 发送者 |
| `goods_rating` | 交易互评（1～5 星 + 评语） | → 订单、→ 评价人、→ 被评价人 |

串起来看：一个用户发布多件商品，另一个用户对某件商品发起会话，聊完下一笔订单，完成后双方各留一条评价。所有功能落到数据库，都是这九张表的增删改查。

### 5.2 订单状态机

**状态机**（State Machine，规定「哪些状态能变成哪些状态」）写在 `goods/models.py:150-162`，视图里逐个校验：

```
pending   待卖家确认  ──卖家确认──→  accepted  待收货  ──确认收货──→  completed 已完成
    │                                   │
    ├──卖家拒绝──→ rejected              └──买家取消──→ cancelled
    └──买家取消──→ cancelled
```

只有 `completed` 之后才能互评。完成后还会做两件联动：商品标记 `is_sold=True`，同一商品其他进行中订单自动关闭（`goods/views.py:507-517`）。

### 5.3 四处唯一约束

**约束（Constraint）** 是数据库层的最后一道兜底，比在代码里写 `if` 可靠——连点两次、网络重试、两个请求同时到达，数据库也只让存一条。

| 位置 | 约束 | 防什么 |
|---|---|---|
| `Favorite` (`models.py:302-304`) | `(user, product)` 唯一 | 重复收藏 |
| `Conversation` (`models.py:373-377`) | `(product, buyer)` 唯一 | 同一件商品被拆成多条聊天 |
| `Order` (`models.py:225-231`) | `(product, buyer)` 在 `status ∈ {pending, accepted}` 时唯一 | **条件唯一约束**：重复下单；但订单完成后允许再买别的 |
| `Rating` (`models.py:462-464`) | `(order, rater)` 唯一 | 同一笔订单重复评价 |

### 5.4 几个值得记住的设计决策

| 决策 | 为什么 |
|---|---|
| 自定义用户模型（`AUTH_USER_MODEL = 'accounts.User'`） | 项目起步就确定扩展点，避免后期迁移内置 User 表的高成本；Django 官方推荐实践 |
| 分类用独立表，不写死成下拉选项 | 后台可随时增删分类，筛选复用同一份数据 |
| 分类外键用 `PROTECT` | 误删分类不会让商品变成「孤儿数据」；卖家外键用 `CASCADE`，删用户连带删商品 |
| 订单存 `price` 快照，不实时读商品价 | 卖家后来改价，也不影响已成交订单 |
| 信用分不存用户表，实时 `aggregate()` 算 | 每笔成交最多 2 条评价，数据量极小；实时算可避免「双写不一致」 |
| 图片 `upload_to="products/%Y/%m/"` | 按年月分目录，避免单目录塞几万张图 |

## 6. 第五层：功能模块逐个拆解

**这一层讲什么**：每个功能「要做什么 / 用到什么 / 关键实现 / 防了什么坑」。建议先挑最短的 6.5 收藏看，附录 A 有它的逐站链路图。

### 6.1 注册登录与个人中心

- **做什么**：注册后自动登录；登录 / 登出；个人中心显示我发布的、买到的、卖出的、收藏的数量。
- **用到什么**：Django 内置 `LoginView` / `LogoutView`、`RegisterForm`（`ModelForm`）、`@login_required` 装饰器。
- **关键实现**：`accounts/views.py:8-19` 校验通过后 `login(request, user)` 直接建立会话；`@login_required` 让未登录访问自动跳到 `LOGIN_URL`。
- **防了什么**：密码用 Django 内置哈希存储，代码里不出现明文密码。

### 6.2 发布闲置与图片上传

- **做什么**：填标题、分类、售价、原价、成色、描述、交易地点、包邮设置，上传封面图。
- **用到什么**：`ModelForm`（由模型自动生成表单）、`ImageField`、`request.FILES`。
- **关键实现**：`goods/forms.py` 给每个字段加 Bootstrap 类、写 `clean_price()` / `clean()` 做服务端校验（价格 > 0、原价 > 售价）；`goods/views.py:127-139` 用 `form.save(commit=False)` 先把 `seller` 设成当前登录用户再保存。
- **防了什么**：**卖家永远取 `request.user`**，不信任前端传来的用户 ID，否则谁都能冒充别人发布。

### 6.3 首页：搜索、筛选与上滑加载

- **做什么**：每页 6 件商品，支持关键词、分类筛选，滑到底自动加载下一页。
- **用到什么**：`Q` 对象（构造「或」条件）、`Paginator`（分页器）、`IntersectionObserver`（浏览器自带的「元素进入视野」观察器）、局部模板。
- **关键实现**（`goods/views.py:44-81`、`home.html:435-484`）：
  - 前端带 `X-Requested-With: XMLHttpRequest` 头请求下一页 → 后端只返回 `partials/product_cards.html` 片段，不重复传整页；
  - 后端用两个自定义响应头 `X-Has-Next` / `X-Next-Page` 告诉前端还有没有下一页；
  - 观察器盯住列表底部的哨兵元素，提前 240px 触发加载；老浏览器退化成滚动监听，加载失败还能回退到手动翻页。
- **防了什么**：`_base_queryset()` 用 `select_related` + `Prefetch` 一次性取好关联数据，避免列表页 **N+1 查询**（渲染 N 张卡片就查 N 次库）这个 Django 最经典的性能坑。

### 6.4 商品详情

- **做什么**：浏览量 +1、同类推荐 3 件、留言板、收藏按钮、卖家信用条。
- **用到什么**：`F()` 表达式、`refresh_from_db`、反向关联查询。
- **关键实现**：`goods/views.py:94` 用 `Product.objects.filter(pk=pk).update(views=F("views") + 1)` 把自增交给数据库原子执行。若写成 `product.views += 1; product.save()`，两个人同时打开就可能丢一次计数。
- **防了什么**：商品不存在时**友好跳回首页并提示**（`views.py:89-93`），而不是甩一张 404 错误页给从旧链接点进来的用户。

### 6.5 收藏（最短的完整闭环）

- **做什么**：一个按钮同时管「加收藏」和「取消收藏」。
- **关键实现**（`goods/views.py:536-547`）：`get_or_create()` 查得到就删、查不到就建；`redirect()` 而不是直接渲染（这个套路叫 **PRG**，Post/Redirect/Get，防止按 F5 重复提交）；`_safe_next()` 只允许站内相对路径跳转，防止 `next` 参数被拿去做开放重定向。
- **防了什么**：`@require_POST` 挡掉 GET 方式的误触发（浏览器预加载、搜索引擎爬过都会发 GET）；`{% csrf_token %}` 挡掉伪造提交。
- 完整逐站链路见 **附录 A**。

### 6.6 私聊（微信式独立会话）

- **做什么**：详情页「我想要」「直接购买」都进入同一个会话；左边会话列表、右边聊天窗；顶部固定商品横幅带橙色「立即购买」；对方消息自动出现。
- **用到什么**：`fetch`、`setInterval` 轮询、`JsonResponse`、`Subquery` / `annotate`、上下文处理器。
- **关键实现**：
  - `chat_start` 用 `get_or_create(product, buyer)` 保证一个买家对一件商品只有一个会话（`views.py:222-225`）；
  - 发消息用 `fetch` 提交 JSON，成功后局部插入气泡（`chat_center.html:505-525`）；
  - 每 3 秒带 `after=最后一条消息ID` 请求 `/chat/<id>/poll/`，只拉新增消息（`views.py:322-343`、`chat_center.html:527-541`）——这是**轮询**（Polling），不是 WebSocket，够用且实现简单；
  - 进入会话即把对方消息批量标为已读；导航 / Tab 栏红点由 `chat_notifications` 上下文处理器统一算。
- **防了什么**：`_conversation_or_404()` 校验「必须是买卖双方之一」，不是就返回 404（**不返回 403，避免暴露这个会话存在**）。

### 6.7 下单：面对面 / 线上双模式

- **做什么**：二选一。面对面=校内自提，不填地址不收运费；线上=填收货人 / 电话 / 地址，按卖家发布时设的「包邮 / 不包邮（¥8）」算运费，可立即模拟支付或稍后支付。
- **用到什么**：`transaction.atomic()`（事务，把几步操作包成「要么全成功要么全回滚」）、`IntegrityError` 捕获。
- **关键实现**：`goods/views.py:368-442`。服务端校验交易方式合法、线上模式收货三件套齐全；`Order.objects.create` 放在事务里，撞上条件唯一约束就捕获异常并提示「你已经下过单了」。
- **防了什么**：重复下单、卖家买自己商品、对已售 / 已预订商品下单；支付是**演示级模拟**，只改订单状态，不接真实支付渠道。

### 6.8 订单状态流转

- **关键实现**：`goods/views.py:473-522`，所有动作（`accept` / `reject` / `cancel` / `pay` / `complete`）在一个接口里按「身份 + 当前状态」双重判断，包在事务里。
- **防了什么**：**前端藏按钮只是体验，不是安全边界**——服务端逐个校验，买家不能去点「确认订单」，卖家不能替别人取消。

### 6.9 信用体系：互评与公开主页

- **做什么**：订单完成后买卖双方各给对方一次 1～5 星 + 评语；公开主页 `/u/<id>/` 显示好评率、均分、成交数、在售商品、收到的评价。
- **关键实现**：`order.can_rate(user)` 把「已完成 / 是当事人 / 没评过」三个条件收进模型（`models.py:277-281`）；`_user_credit()` 用 `aggregate(Count, Avg)` 实时算（`views.py:584-597`）；`seller_profile` 无需登录即可访问。
- **防了什么**：重复评价（唯一约束 + `IntegrityError` 双保险）、未完成订单评价、非当事人评价。
- **一个真实的坑**：`urls.py:24-26` 有注释——`orders/<int:pk>/rate/` 必须排在 `orders/<int:pk>/<str:action>/` **前面**，否则 `rate` 会被当成 `action` 吞掉，落到只收 POST 的路上，GET 评价页就变成 405。Django 路由**从上往下匹配，第一条命中就停**。

### 6.10 手机端底部 Tab 栏

- **做什么**：窄屏时贴底显示「首页 / 发布 / 消息 / 我的」，发布居中凸起，当前页高亮，消息带未读红点，聊天页自动隐藏。
- **用到什么**：**CSS 媒体查询**（`@media (max-width: 767.98px)`，一句「屏幕窄于某宽度才生效」的规则）、`env(safe-area-inset-bottom)` 适配全面屏下巴、上下文变量。
- **关键实现**：全部在 `base.html:401-439, 527-545`，**没碰一行 Python，也没碰数据库**——这就是模板继承的威力。
- **防了什么**：聊天页自己有输入条，用 `body.chat-app` 把 Tab 栏隐藏，避免两个底栏叠在一起。

### 6.11 PWA：添加到主屏幕

- **做什么**：手机「添加到主屏幕」后全屏打开，有独立品牌图标。
- **用到什么**：`manifest.webmanifest`（应用清单）、`sw.js`（**Service Worker**，浏览器后台的一段代理脚本）、3 档 PNG 图标（Pillow 画的纸箱笑脸）。
- **关键实现**：三个文件必须挂在**站点根路径**，Service Worker 的作用域才是整个站点（`config/urls.py:10-13`）；视图用 `JsonResponse` / `HttpResponse` / `FileResponse` 直接返回，不依赖静态文件收集（`views.py:737-754`）。
- **防了什么（这条很关键）**：SW **只缓存站内图片，绝不缓存 HTML**。因为页面里含一次性 CSRF 凭证，缓存旧页面会让凭证过期复用，重演手机登录 403。这是把前面的坑提前堵住，而不是等它再发生。

## 8. 部署与数据持久化

**这一层讲什么**：线上是怎么跑起来的，以及那个最痛的坑是怎么从根上修掉的。
**会碰到的新词**：环境变量、反向代理、持久化、DEBUG、种子数据。

### 8.1 本地运行

```bash
pip install -r requirements.txt     # 装依赖（只有 Django 和 Pillow）
python manage.py migrate           # 按迁移说明书建表
python manage.py seed_demo         # 灌演示数据：6 分类 / 4 用户 / 8 商品 / 订单 / 留言 / 私聊 / 评价
python manage.py runserver         # 启动开发服务器
```

然后访问 `http://127.0.0.1:8000`。模板改动不用重启服务，刷新即可；改了 `.py` 开发服务器会自动重载。

### 8.2 线上启动脚本做了什么

部署平台只注入一个 HTTP 端口（`PORT`），且启动命令里的 `$PORT` 不一定被 shell 展开，所以用 Python 写了 `start.py` 直接读环境变量。它按顺序做四件事：

```
① bootstrap_data_dir()  首次运行：把随代码上传的 db.sqlite3 / media 复制成种子
                          （copytree 的 dirs_exist_ok=True 表示合并，不覆盖已有图片）
② 设置 XJ_DATA_DIR      指向 ~/.xianxiaoji（发布目录之外）
③ migrate + seed_demo   对齐表结构；幂等补齐演示数据（只补缺失，不动用户内容）
④ os.execv(...)         用 Python 读到的 PORT 启 runserver，--noreload 常驻
```

### 8.3 数据为什么会丢，又是怎么修的

**现象**：朋友刚注册发布的两件商品，一次重新发布后不见了。

**根因**：`db.sqlite3` 和用户上传的 `media/` 原本都放在**项目目录里**。发布是「把整个源码目录覆盖上传」，于是数据库文件被随包附带的旧种子库覆盖——代码更新一次，真实数据就清零一次。这不是代码逻辑错，是**存储位置错**。

**修法**（`settings.py:12, 76, 103`）：

```python
DATA_DIR = Path(os.environ.get("XJ_DATA_DIR") or BASE_DIR)
DATABASES['default']['NAME'] = DATA_DIR / 'db.sqlite3'
MEDIA_ROOT = DATA_DIR / 'media'
```

本地不设 `XJ_DATA_DIR` 时 `DATA_DIR` 就是项目目录，开发体验不变；线上由 `start.py` 指向 `~/.xianxiaoji`，**代码目录怎么覆盖都碰不到数据**。修完用「模拟连续发布两次」验证过，账号和商品都还在。

> 旧数据无法恢复（被覆盖后没有备份），这是本次项目唯一一次真实数据损失，也是代价最大的一课：**数据必须和代码分开存放**。

### 8.4 可配置的环境变量

| 变量 | 作用 | 默认值 |
|---|---|---|
| `XJ_DATA_DIR` | 数据库与上传图片的持久目录 | 项目根目录 |
| `XJ_SECRET_KEY` | 签名密钥（会话 / CSRF 都靠它） | 开发用固定值 |
| `XJ_CSRF_ORIGINS` | 受信任来源，多个用英文逗号分隔 | 当前线上域名 |
| `PORT` | HTTP 端口（由部署平台注入） | `3000` |

### 8.5 当前状态与生产化建议

`DEBUG = True` 目前是**刻意保留**的：线上商品图由 runserver 的静态服务直接提供（`config/urls.py:20-21`），关掉 DEBUG 图片就会 404。若真要上生产，需要按顺序改四件事：

1. 用 Nginx 托管 `MEDIA_ROOT`，然后关闭 `DEBUG`；
2. `ALLOWED_HOSTS` 从 `['*']` 收紧到具体域名；
3. `SECRET_KEY` 走环境变量，不写进仓库；
4. 换 PostgreSQL / MySQL 并把 `runserver` 换成 gunicorn + WSGI。

## 9. 踩坑复盘：六个真实问题

**这一层讲什么**：把开发过程中真实撞到的坑，按「现象 → 根因 → 怎么查 → 怎么防」排成错题本。每个都是教科书级知识点，比刷教程记得牢。

### 9.1 手机登录 403

| | |
|---|---|
| 现象 | 电脑正常，手机点登录报 403 |
| 根因 | 站点在**反向代理**后面，浏览器带来的 `Origin` 是公网域名，没进 `CSRF_TRUSTED_ORIGINS`，Django 门卫不认这张凭证 |
| 怎么查 | 看请求头 `Origin` 与 `Referer`，对照 `settings.py` 的受信任列表 |
| 怎么防 | 加 `CSRF_TRUSTED_ORIGINS`，并改用环境变量 `XJ_CSRF_ORIGINS` 以便换域名；用带 `enforce_csrf_checks` 的测试客户端验证陌生 Origin 仍被拒 |

### 9.2 点商品跳 404

| | |
|---|---|
| 现象 | 线上点某件商品直接 404 |
| 根因 | 数据库被发布覆盖，那个 `pk` 对应的商品已经不存在；模板里仍留着旧链接 |
| 怎么查 | 直接查库里 `Product.objects.filter(pk=...)` 是否存在 |
| 怎么防 | 详情页捕获 `Product.DoesNotExist` → 提示后跳首页（`views.py:89-93`）；启动时幂等补种子；**根上是 8.3 的数据持久化** |

### 9.3 数据被发布覆盖（最痛的一次）

见 8.3。教训：**代码可以反复覆盖，数据不可以**。任何「发布 = 覆盖目录」的部署方式，都必须先把数据目录挪出去。

### 9.4 评价页变成 405

| | |
|---|---|
| 现象 | 打开 `/orders/12/rate/` 返回 405 |
| 根因 | 路由表里 `orders/<int:pk>/<str:action>/` 排在前面，`rate` 被当成 `action` 吞掉，落到 `order_action` 这个只收 POST 的视图上，GET 被拒 |
| 怎么查 | 打印实际命中的视图，比对 `urls.py` 顺序 |
| 怎么防 | 把具体路由 `orders/<int:pk>/rate/` 移到通配路由**之前**（`urls.py:24-26` 已留注释）；记住 Django 路由**从上往下、首条命中即停** |

### 9.5 聊天页被压窄

| | |
|---|---|
| 现象 | 微信式双栏聊天页在桌面端只占中间一条，左右留白巨大 |
| 根因 | 外层 `main { display: flex }` 让页面容器被当弹性子项收缩 |
| 怎么查 | 浏览器开发者工具看盒模型宽度 |
| 怎么防 | 改 `flex-direction: column`，让 `.page-wrap` 铺满宽度；聊天页用独立 `body.chat-app` 类控制布局 |

### 9.6 PWA 缓存与 CSRF（预防性决策）

Service Worker 若缓存整个 HTML，页面里的一次性 CSRF 凭证会过期复用，等于把 9.1 的坑再踩一遍。因此 `sw.js` 明确跳过 `req.mode === 'navigate'` 与非 GET 请求，**只缓存 `/media/` 和 `/pwa/` 下的图片**（`views.py:716-721`）。这是「从坑里推出来的设计」，不是事后补丁。

### 9.7 一个假警报

用无头浏览器截图验证移动端时，发现「页面横向溢出」，后来确认是**无头 Edge 最小窗宽 500px** 造成的假象，不是 CSS 问题。用 500px 宽度单独截图后布局正常。教训：**先确认测量工具本身的限制，再怀疑代码**。

## 附录 A：一次「收藏」点击的完整链路

整个项目里最短、但五脏俱全的一条链路。理解它，就理解了所有功能。

```
① 浏览器  templates/product_detail.html:113-122
   <form method="post" action="{% url 'favorite_toggle' product.pk %}">
     {% csrf_token %}  <button>收藏这件好物</button>
   </form>
   ↓ 为什么用 post 不用 <a href>？因为点一下会改数据库；
     链接会被浏览器预加载 / 刷新 / 爬虫误触发。

② 路由    goods/urls.py:11
   path("product/<int:pk>/favorite/", views.favorite_toggle, name="favorite_toggle")
   把网址里的数字抓出来当 pk 交给视图（从上往下，首条命中即停）。
   ↓
③ 安检    settings.py:41-49
   SessionMiddleware 认出你是谁 → CsrfViewMiddleware 验凭证。
   ↓
④ 视图    goods/views.py:536-547（真正的核心，只有 5 行）
   favorite, created = Favorite.objects.get_or_create(user=request.user, product=product)
   if created: 提示「已加入收藏」
   else:       favorite.delete()          ← 一个接口同时管加和删
   return redirect(...)                  ← PRG，防刷新重复提交
   ↓
⑤ 模型    goods/models.py:284-304
   UniqueConstraint(fields=["user", "product"])   ← 数据库层兜底防重复
   ORM 翻译成 INSERT / DELETE 写进 db.sqlite3
   ↓
⑥ 模板    views.py → product_detail 重新查 is_favorited
   按钮文字变成「已收藏 · 点击取消」，收藏数 +1
   ↓
⑦ 响应    新的一份 HTML 送回浏览器，画成页面。一圈走完。
```

**这条链路里藏着五个知识点**：POST 与 GET 的语义区别、CSRF、框架路由的匹配顺序、`get_or_create` 的幂等切换、PRG 与数据库唯一约束的双保险。其他十几个功能，都是这条链路换了张表和一段判断。
