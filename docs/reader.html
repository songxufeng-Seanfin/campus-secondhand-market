1.1 解决什么问题

校园里买卖二手书、自行车、耳机，通常靠微信群刷屏：信息一闪就过、没法按分类找、也不好判断对方靠不靠谱。「闲小集」把它做成一个有商品列表、有详情页、能私聊议价、能下单、能互评的小集市，全部围绕「校内自提、学生之间交易」这个场景。

2. 第一层：从屏幕到服务器

这一层讲什么：按一次刷新，背后发生了什么；那些看不懂的三位数报错，到底卡在哪一站。 会碰到的新词：请求、响应、状态码、客户端 / 服务端、CDN。

2.1 一次点击 = 跑一圈

整个网站所有变化，都是同一圈在反复跑：

你点一下 / 按 F5
    ↓  浏览器发出「请求」（带上网址、填的表单、登录小票）
服务器（一台一直开着、跑着我们代码的电脑）
    ↓  照着网址跑一圈：安检 → 找路 → 干活 → 拼页面
    ↑  回送「响应」：一份 HTML 文本
浏览器把 HTML 画成页面

关键认知：页面不会自己变。收藏数变了、来了条新消息，都是又跑了一圈（或由 JavaScript 悄悄再跑一小圈）。

一次刷新其实不止一圈：先取页面这一圈；页面里的 CSS、JS、商品图片又各自发请求去取。你只按了一下，背后是好几圈。

2.2 网址说了两件事

https://xianxiaoji-market.app.workbuddy.host/product/8/
└──────────── 找哪台服务器 ────────────┘└─ 找哪条路 ─┘

前半段由域名解析找到服务器；后半段 /product/8/ 交给服务器里的路由表去分诊。这里的「路由」是网站内部的一张网址分诊表，不是家里那个路由器设备。

2.3 状态码：报错终于有位置了

代号定义（永远不变）本项目里那次的具体原因
404这条路没找到线上数据被发布覆盖，商品 id 不存在了
405路找到了，但请求方式不对rate 被通配路由吞掉，落到只收 POST 的路上，GET 被拒
403门卫不认凭证公网域名没进受信任列表，手机登录带的一次性凭证被拦
500里面某段代码执行出错项目里没真正出现过；全站巡检就是专门查它
记法：404 找不着路、405 方式不对、403 不让进、500 里面出错。
容易混的一点：「定义」和「那次为什么撞上」是两回事。「被覆盖」不是 404 的定义，只是那一次让路消失的原因；换任何一个不存在的商品，一样是 404。

3. 第二层：Django 收到请求之后的流水线

这一层讲什么：把上一章那「一圈」拆开，看框架内部怎么分活、怎么记住你是谁。 会碰到的新词：框架、MVT、中间件、Session / Cookie、CSRF、ORM、request.user。

3.1 「框架」和「工具」的区别

Django 不是我们写的，是别人已经盖好水电的楼。登录注册、后台管理、门卫、数据库读写这些通用活它自带，我们只往里填「商品 / 订单 / 评价」这些房间。

有个反转值得记：Pillow 那种工具是你叫它干活（说「裁图」，它就裁）；Django 这种框架反过来，是它来叫你——网址命中了，它跑去调我们写的那个函数。流程是框架定好的，我们只往固定格子里填内容。所以叫「框架」不叫「工具包」。

Django 用的是 MVT（模型 - 模板 - 视图） 分层，和常见的 MVC 是同一类思想，只是名字不同：

MVT白话文件
Model 模型数据长什么样、存在哪models.py
View 视图收到请求后干什么活views.py
Template 模板把数据摆成页面templates/*.html

3.2 六站流水线

站名称干什么谁提供的
1中间件（Middleware，请求进门先过的几道固定安检）认出登录的人、验表单凭证Django 自带，顺序写在 settings.py:41-49
2路由（URLconf，网址分诊表）这个网址交给哪个函数我们写一张表 goods/urls.py
3视图（View）查什么数据、改成什么我们写 goods/views.py
4模型 / ORM → 数据库把 Python 翻成数据库指令，读写 db.sqlite3Django 翻译，表结构我们定
5模板（Template）把数据排成 HTML我们写 templates/*.html
6响应（Response）HTML 送回浏览器Django 自带

看这张表能发现一件事：六格里真正属于我们写的只有中间四格，而且都是「填内容」，不是「造流程」。这就是「项目里自己的代码比看上去少得多」的原因。

3.3 四个关键词的白话版

  • Session / Cookie（会话 / 小票）：登录成功后服务器给浏览器一张小票，之后每次请求自动带着；服务器凭小票认出你是谁。这个被认出来的人，在代码里就叫 request.user。所以收藏按钮不用写用户名，也替不了别人收藏（goods/views.py:541）。
  • CSRF（跨站请求伪造防护）：安检里的那个门卫。每个表单藏一张一次性凭证（{% csrf_token %}），确认「这请求真是我自己的页面发出的」。手机登录 403 那次，就是这张凭证和线上域名对不上。
  • ORM（对象关系映射）：模型那一站的翻译官。我们只写「取这个用户收藏的商品」这样的 Python，不用手写 SQL（数据库查询语言），Django 负责翻译。
  • 上下文处理器（Context Processor）：网站自动塞给所有页面的现成信息。导航栏未读红点就是这么来的——写在 goods/context_processors.py，在 settings.py:64 注册一次，首页、详情页全都自动有。

3.4 顺带解释那次最痛的事

朋友发布的商品不见了，不是代码写错，是「东西放在哪」的问题：数据库文件跟着项目目录走，发布时整个目录被覆盖，它就一起没了。后来把数据挪到发布目录之外（第 8 章），就再没丢过。这件事落在流水线的第 4 站。

4.2 三个「应用」

Django 把一个大项目拆成若干 App（应用，可复用的功能模块）。本项目两个：

  • accounts：只管「谁在用」——注册、登录、个人中心。
  • goods：管「集市里发生的一切」——商品、订单、收藏、留言、私聊、评价。

登录登出甚至没自己写视图，直接复用 Django 内置的 LoginView / LogoutView（accounts/urls.py:9-14），这就是「框架自带水电」的意思。

4.3 迁移是什么

改了 models.py（比如给订单加「运费」字段），数据库不会自己变。迁移（Migration） 就是一份「数据库结构变更说明书」：

python manage.py makemigrations goods   # 对比模型与现有结构，生成一份变更说明书
python manage.py migrate               # 按说明书真的去改数据库

项目里 goods/migrations/ 有四份：

文件对应哪次功能
0001_initial.py分类、商品表
0002_...py订单、收藏、商品留言
0003_...py双模式交易（地址 / 运费 / 支付状态）
0004_rating.py交易评价

为什么要提交这些文件？ 因为队友拉下代码后跑一次 migrate，就能得到一模一样的表结构；start.py 在线上启动时也是这么做的。

4.4 模板继承

base.html 是所有页面共用的外壳：导航栏、设计变量、页脚、手机 Tab 栏、PWA 标签、Bootstrap 引入，全写在这一份里。其他模板第一行都是 {% extends "base.html" %}，只填中间那块内容。所以「加一条手机底部栏」只改一个文件，全站十几页就都有了。

5. 第四层：数据层设计

这一层讲什么：数据长什么样、表之间怎么连、为什么加约束、状态怎么流转。 会碰到的新词：表 / 字段 / 主键 / 外键、约束、索引、事务、状态机、聚合。

5.1 九张表与关系

表白话：存什么关键外键
accounts_user用户（用户名、密码哈希、手机号、头像）—
goods_category6 个分类（教材书籍 / 数码电子 / …）—
goods_product商品（标题、描述、售价、原价、成色、封面、地点、包邮设置、浏览量、是否售出）→ 卖家、→ 分类
goods_order订单（成交价快照、交易方式、收货信息、运费、支付状态、状态）→ 商品、→ 买家、→ 卖家

串起来看：一个用户发布多件商品，另一个用户对某件商品发起会话，聊完下一笔订单，完成后双方各留一条评价。所有功能落到数据库，都是这九张表的增删改查。

5.2 订单状态机

状态机（State Machine，规定「哪些状态能变成哪些状态」）写在 goods/models.py:150-162，视图里逐个校验：

pending   待卖家确认  ──卖家确认──→  accepted  待收货  ──确认收货──→  completed 已完成
    │                                   │
    ├──卖家拒绝──→ rejected              └──买家取消──→ cancelled
    └──买家取消──→ cancelled

只有 completed 之后才能互评。完成后还会做两件联动：商品标记 is_sold=True，同一商品其他进行中订单自动关闭（goods/views.py:507-517）。

5.3 四处唯一约束

约束（Constraint） 是数据库层的最后一道兜底，比在代码里写 if 可靠——连点两次、网络重试、两个请求同时到达，数据库也只让存一条。

位置约束防什么
Favorite (models.py:302-304)(user, product) 唯一重复收藏
Conversation (models.py:373-377)(product, buyer) 唯一同一件商品被拆成多条聊天

5.4 几个值得记住的设计决策

决策为什么
自定义用户模型（AUTH_USER_MODEL = 'accounts.User'）项目起步就确定扩展点，避免后期迁移内置 User 表的高成本；Django 官方推荐实践
分类用独立表，不写死成下拉选项后台可随时增删分类，筛选复用同一份数据
分类外键用 PROTECT误删分类不会让商品变成「孤儿数据」；卖家外键用 CASCADE，删用户连带删商品
订单存 price 快照，不实时读商品价卖家后来改价，也不影响已成交订单
信用分不存用户表，实时 aggregate() 算每笔成交最多 2 条评价，数据量极小；实时算可避免「双写不一致」
图片 upload_to="products/%Y/%m/"按年月分目录，避免单目录塞几万张图

  • 关键实现：goods/views.py:473-522，所有动作（accept / reject / cancel / pay / complete）在一个接口里按「身份 + 当前状态」双重判断，包在事务里。

  • 做什么：手机「添加到主屏幕」后全屏打开，有独立品牌图标。

8.3 数据为什么会丢，又是怎么修的

现象：朋友刚注册发布的两件商品，一次重新发布后不见了。

根因：db.sqlite3 和用户上传的 media/ 原本都放在项目目录里。发布是「把整个源码目录覆盖上传」，于是数据库文件被随包附带的旧种子库覆盖——代码更新一次，真实数据就清零一次。这不是代码逻辑错，是存储位置错。

修法（settings.py:12, 76, 103）：

DATA_DIR = Path(os.environ.get("XJ_DATA_DIR") or BASE_DIR)
DATABASES['default']['NAME'] = DATA_DIR / 'db.sqlite3'
MEDIA_ROOT = DATA_DIR / 'media'

本地不设 XJ_DATA_DIR 时 DATA_DIR 就是项目目录，开发体验不变；线上由 start.py 指向 ~/.xianxiaoji，代码目录怎么覆盖都碰不到数据。修完用「模拟连续发布两次」验证过，账号和商品都还在。

旧数据无法恢复（被覆盖后没有备份），这是本次项目唯一一次真实数据损失，也是代价最大的一课：数据必须和代码分开存放。

9. 踩坑复盘：六个真实问题

这一层讲什么：把开发过程中真实撞到的坑，按「现象 → 根因 → 怎么查 → 怎么防」排成错题本。每个都是教科书级知识点，比刷教程记得牢。

9.1 手机登录 403

现象电脑正常，手机点登录报 403
根因站点在反向代理后面，浏览器带来的 Origin 是公网域名，没进 CSRF_TRUSTED_ORIGINS，Django 门卫不认这张凭证
怎么查看请求头 Origin 与 Referer，对照 settings.py 的受信任列表
怎么防加 CSRF_TRUSTED_ORIGINS，并改用环境变量 XJ_CSRF_ORIGINS 以便换域名；用带 enforce_csrf_checks 的测试客户端验证陌生 Origin 仍被拒

9.2 点商品跳 404

现象线上点某件商品直接 404
根因数据库被发布覆盖，那个 pk 对应的商品已经不存在；模板里仍留着旧链接
怎么查直接查库里 Product.objects.filter(pk=...) 是否存在
怎么防详情页捕获 Product.DoesNotExist → 提示后跳首页（views.py:89-93）；启动时幂等补种子；根上是 8.3 的数据持久化

9.3 数据被发布覆盖（最痛的一次）

见 8.3。教训：代码可以反复覆盖，数据不可以。任何「发布 = 覆盖目录」的部署方式，都必须先把数据目录挪出去。

9.4 评价页变成 405

现象打开 /orders/12/rate/ 返回 405
根因路由表里 orders/<int:pk>/<str:action>/ 排在前面，rate 被当成 action 吞掉，落到 order_action 这个只收 POST 的视图上，GET 被拒
怎么查打印实际命中的视图，比对 urls.py 顺序
怎么防把具体路由 orders/<int:pk>/rate/ 移到通配路由之前（urls.py:24-26 已留注释）；记住 Django 路由从上往下、首条命中即停

9.5 聊天页被压窄

现象微信式双栏聊天页在桌面端只占中间一条，左右留白巨大
根因外层 main { display: flex } 让页面容器被当弹性子项收缩
怎么查浏览器开发者工具看盒模型宽度
怎么防改 flex-direction: column，让 .page-wrap 铺满宽度；聊天页用独立 body.chat-app 类控制布局

9.6 PWA 缓存与 CSRF（预防性决策）

Service Worker 若缓存整个 HTML，页面里的一次性 CSRF 凭证会过期复用，等于把 9.1 的坑再踩一遍。因此 sw.js 明确跳过 req.mode === 'navigate' 与非 GET 请求，只缓存 /media/ 和 /pwa/ 下的图片（views.py:716-721）。这是「从坑里推出来的设计」，不是事后补丁。

9.7 一个假警报

用无头浏览器截图验证移动端时，发现「页面横向溢出」，后来确认是无头 Edge 最小窗宽 500px 造成的假象，不是 CSS 问题。用 500px 宽度单独截图后布局正常。教训：先确认测量工具本身的限制，再怀疑代码。

写在前面

校园里卖闲置，大多靠群聊刷屏：一本书的照片发出来，三分钟就被新消息顶没了；想找辆自行车得翻半天聊天记录；交易全靠「你信我我也信你」。

所以我想做的不是又一个「商品展示页」，而是一个能走完整条链路的小集市：从发布、浏览、议价，到下单、完成交易、互相评价。这篇文章记录它是怎么一层层搭起来的，也记录几个把我卡了很久的坑。

写得多了才发现，十几个功能其实是同一套骨架重复搭了很多遍，这篇就按这个顺序往下记。

一、先看成品：四块功能

二、技术选型：为什么是 Django

先说一个我后来才想明白的区别：工具是你叫它干活，框架是它来叫你。

Pillow（Python 的图片处理库）是工具——我说「把这张图裁成 1200×900」，它裁完就完事。Django 是框架：网址命中了，它反过来去调用我写的那个函数。流程、登录、后台、防伪造提交、数据库读写，全是它自带的；我只往固定格子里填「商品 / 订单 / 评价」这些房间。

这带来的直接好处是：依赖只有两个。

Django==5.2.*
Pillow

没有 npm、没有 webpack、没有前端构建。Bootstrap 5 和图标库从 CDN（内容分发网络，别人托管好的公共文件）直接引用，样式写在模板里。对一个练手项目来说，这个简单度非常关键——我不用先学会五套工具链，才能看到第一个页面。

Django 用的是 MVT 分层，说白了就是把事情拆成三份：

  • M（Model 模型）：数据长什么样、存在哪 → models.py
  • V（View 视图）：收到请求后干什么活 → views.py
  • T（Template 模板）：把数据摆成页面 → templates/*.html

数据库选了 SQLite：整个库就是一个 db.sqlite3 文件，零配置、能直接拷走。对本地开发和演示足够，后期换 MySQL / PostgreSQL 也只是改 settings.py 里的一个配置。

三、整个系统的骨架：一次点击走一圈

这是我觉得最值钱的一张图，因为所有功能都是这一圈在反复跑：

你点一下按钮
   ↓  浏览器发出「请求」：网址 + 表单内容 + 登录小票
服务器照着网址跑一圈
   安检 → 路由分诊 → 视图干活 → 读写数据库 → 模板拼页面
   ↑  回送「响应」：一份 HTML
浏览器把 HTML 画成页面

页面不会自己变。收藏数变了、来了条新消息，都是又跑了一圈（或由 JavaScript 悄悄再跑一小圈）。而且一次刷新其实不止一圈：先取页面，页面里的 CSS、脚本、商品图片又各自发请求去取。

把 Django 内部那一圈拆开，是六站：

站干什么谁提供的
1 中间件认出登录的人、验表单凭证Django 自带
2 路由这个网址交给哪个函数我写一张表
3 视图查什么数据、改成什么我写
4 模型 / 数据库把 Python 翻成数据库指令Django 翻译，表结构我定
5 模板把数据排成 HTML我写
6 响应送回浏览器Django 自带

六站里真正属于我写的只有中间四格，而且都是「填内容」，不是「造流程」。 想通这一点，项目一下子从「五千行天书」变成了「四格填空」。

顺带，那些曾经看不懂的三位数报错，也终于有位置了：

代号意思我这次撞上的具体原因
404找不着路线上数据被发布覆盖，那个商品 id 不存在了
405路找到了，方式不对rate 被通配路由吞掉，落到只收 POST 的路上
403门卫不认凭证公网域名没进受信任列表，手机登录被拦

记法：404 找不着路、405 方式不对、403 不让进、500 里面出错。要注意「代号的定义」和「那次为什么撞上」是两回事——「被覆盖」不是 404 的定义，只是那一次让路消失的原因。

四、数据怎么设计：九张表撑起整个集市

想清楚「存什么」，功能就成型了一半。九张表：用户、分类、商品、订单、收藏、商品留言、私聊会话、会话消息、交易评价。

串起来看：一个用户发布多件商品，另一个用户对某件商品发起会话，聊完下一笔订单，完成后双方各留一条评价。

订单是个状态机

状态机就是规定「哪些状态能变成哪些状态」：

pending 待确认 ──卖家确认──→ accepted 待收货 ──确认收货──→ completed 已完成
    │                            │
    ├──卖家拒绝──→ rejected      └──买家取消──→ cancelled
    └──买家取消──→ cancelled

只有走到 completed 才能互评。完成那一刻还会做两件联动：商品标记「已售出」，同一件商品其他进行中的订单自动关闭——不然一件东西会被卖给两个人。

四个唯一约束

约束是数据库层的最后一道兜底，比在代码里写 if 可靠：连点两次、网络重试、两个请求同时到达，数据库也只让存一条。

约束防什么
(用户, 商品) 收藏唯一重复收藏
(商品, 买家) 会话唯一同一件商品被拆成好几条聊天
(商品, 买家) 在订单进行中时唯一重复下单；但订单结束后允许再买
(订单, 评价人) 唯一一笔订单重复评价

第三条是条件唯一约束（只在满足条件的行上生效），写起来是这样：

models.UniqueConstraint(
    fields=["product", "buyer"],
    condition=Q(status__in=["pending", "accepted"]),
    name="uniq_active_order_per_buyer_product",
)

另外两个我挺喜欢的小决策：

  • 订单存成交价快照，不实时读商品价——卖家后来改价，不影响已成交的订单；
  • 信用分不存用户表，用 aggregate(Count, Avg) 实时算——每笔成交最多 2 条评价，数据量极小，实时算反而避免了「两处数据对不上」。

五、几个让我真正理解 Web 的实现

1）收藏：最短的一条完整闭环

它是全项目最短、但五脏俱全的功能，五站全走一遍：

# goods/views.py
favorite, created = Favorite.objects.get_or_create(
    user=request.user, product=product
)
if created:
    messages.success(request, "已加入收藏")
else:
    favorite.delete()          # 一个接口同时管「加」和「删」
return redirect(...)           # 提交后重定向，防刷新重复提交
  • 表单用 method="post" 而不是链接：因为点一下会改数据库，链接会被浏览器预加载 / 刷新 / 爬虫误触发；
  • {% csrf_token %} 藏一张一次性凭证，确认「这请求真是我自己的页面发的」；
  • 用户身份取 request.user（服务器从登录态认出来的人），不信任前端传的用户名，否则谁都能替别人收藏；
  • redirect 而不是直接渲染（这个套路叫 PRG），按 F5 不会重复提交。

其他十几个功能，都是这条链路换了张表和一段判断。

2）上滑自动加载

首页每页 6 件。前端用浏览器自带的 IntersectionObserver（元素进入视野就通知）盯住列表底部的哨兵，提前 240px 触发；请求时带一个 X-Requested-With 头，后端就只返回商品卡片片段，不重复传整页；再用两个自定义响应头 X-Has-Next / X-Next-Page 告诉前端还有没有下一页。

老浏览器退化成滚动监听，加载失败还能回退到手动翻页——降级方案比主方案更容易被忽略，但它决定了用户会不会卡死在空白页。

3）私聊：轮询就够了

详情页「我想要」和「直接购买」进的是同一个会话（靠唯一约束保证）。聊天页是微信式双栏：左边会话列表，右边对话窗，顶部钉着商品横幅和橙色「立即购买」。

发消息用 fetch 局部插入气泡，不整页刷新；每 3 秒带「最后一条消息 ID」去问一次有没有新消息，只拉增量。这叫轮询（Polling），不是 WebSocket，但对校园集市这个量级完全够用，实现也简单得多。

未读红点没有单独做通知表：ChatMessage 上有个 is_read 字段，再用上下文处理器（自动塞给所有页面的变量）统一算一次，导航栏和手机 Tab 栏就都有了。

4）下单双模式与服务端校验

面对面交易 = 校内自提，不填地址不收运费；线上交易 = 填收货人 / 电话 / 地址，按卖家发布时设的「包邮 / 不包邮（¥8）」算运费，可立即模拟支付。

下单动作包在 transaction.atomic()（事务：几步操作要么全成功要么全回滚）里，撞上唯一约束就捕获 IntegrityError 并提示「你已经下过单了」。订单状态流转同理，所有动作都按「身份 + 当前状态」双重判断——前端藏按钮只是体验，不是安全边界，服务端必须自己再验一遍。

六、最痛的一个坑：朋友发布的商品消失了

这个必须单独写一节。

朋友在线上注册、发了两件商品，我更新了一版代码重新发布，商品没了。

根因不是代码写错，是「东西放在哪」错了：db.sqlite3 和用户上传的 media/ 原本都放在项目目录里，而发布是「把整个源码目录覆盖上传」。于是每次更新代码，随包附带的旧数据库就把真实数据冲掉了。代码可以反复覆盖，数据不可以。

修法是把数据和代码分开：

# config/settings.py
DATA_DIR = Path(os.environ.get("XJ_DATA_DIR") or BASE_DIR)
DATABASES["default"]["NAME"] = DATA_DIR / "db.sqlite3"
MEDIA_ROOT = DATA_DIR / "media"

本地不设 XJ_DATA_DIR 时，数据仍在项目目录，开发体验不变；线上启动脚本把它指向 ~/.xianxiaoji（发布目录之外），源码目录怎么覆盖都碰不到数据。修完我模拟连续发布两次验证，账号和商品都还在。

旧数据没能恢复——被覆盖后没有备份。这是整个项目代价最大的一课，也是我现在做任何项目都会先问的一句：这个东西会被重新部署冲掉吗？

顺带一提，线上启动脚本 start.py 也踩了个小坑：部署平台只注入一个 PORT 环境变量，而启动命令里的 $PORT 不一定会被 shell 展开，所以最后用 Python 直接 os.environ.get("PORT") 读，再启服务。

七、另外三个坑，每个都是一节课

手机登录 403：电脑正常、手机不行。因为站点在反向代理后面，浏览器带来的 Origin 是公网域名，没进 CSRF_TRUSTED_ORIGINS，Django 的门卫不认那张凭证。加上受信任来源后就好了，我还把它改成可配置的环境变量，换域名不用改代码。

点商品 404：和上面那个数据丢失是同一根。除了根治存储位置，详情页也加了兜底——商品不存在时提示后跳回首页，而不是甩一张错误页给从旧链接点进来的用户。

评价页 405：路由表里 orders/<id>/<str:action>/ 写在前面，rate 被当成 action 吞掉，落到只收 POST 的视图上，GET 就被拒。Django 路由从上往下匹配，第一条命中就停，把具体路由挪到通配路由前面就好了（代码里留了注释，防止以后再犯）。

还有一个预防性设计值得记：做 PWA 时，Service Worker（浏览器后台的代理脚本）只缓存站内图片，绝不缓存 HTML。因为页面里含一次性 CSRF 凭证，缓存旧页面会让凭证过期复用，等于把 403 那个坑再踩一遍。把前面的教训提前堵住，比事后修舒服得多。

最后是个假警报：用无头浏览器验证手机端时看到「横向溢出」，紧张了半天，结果是无头 Edge 最小窗宽 500px 造成的假象，不是 CSS 问题。教训：先确认测量工具本身的限制，再怀疑代码。

八、手机端：一条栏和一个图标

顶部导航在手机上很挤，常用的四个入口要一步点到。于是加了贴底 Tab 栏「首页 / 发布 / 消息 / 我的」，发布居中凸起，当前页高亮，消息带未读红点。

实现全在 base.html 一份文件里：用 CSS 媒体查询（一句「屏幕窄于 767px 才生效」的规则）控制显示，env(safe-area-inset-bottom) 适配全面屏下巴，聊天页因为有输入条就自动隐藏。因为所有页面都继承这份外壳，改一处，十几页全都有了，一行 Python 都没动。

PWA 那部分则是三个根路径文件：manifest.webmanifest（应用清单，声明全屏启动和图标）、sw.js（缓存脚本）、三档品牌图标（Pillow 画的纸箱笑脸）。挂到根路径是为了让 Service Worker 的作用域覆盖整个站点。

九、怎么确认它「真的能用」

我没有只靠肉眼看页面。收尾时做了两类检查：

  1. 全站巡检：列出 21 个地址，用 Django 的测试客户端（django.test.Client，不启服务器也能模拟浏览器发请求）在已登录 / 未登录两种状态各跑一遍，共 42 次请求，确认没有 500、图标不缺、PWA 标签齐全；
  2. 写操作冒烟测试：越权改别人商品应被 404 拦、收藏加 / 删、留言写入、发私聊消息、完整走一遍「下单 → 卖家确认 → 完成 → 评价」。测完把造出来的临时订单、留言、消息全清掉，不留脏数据。

外加桌面 / 手机两种宽度的截图核对布局。所谓「测试」，说白了就是：模拟点一下按钮，然后检查结果对不对——名字唬人，内容很朴素。

十、回头看：这个项目到底给了我什么

功能清单可以罗列很长，但真正留下的是三样东西。

最明显的是看东西的方式变了。 以前看到一个页面是一整块；现在会自动拆：谁画的（HTML/CSS）、网址交给谁（路由）、干了什么活（视图）、存在哪（模型 / 数据库）。拆开之后，报错不再是天书，而是「卡在第几站」。

另一个是「防」比「做」更花时间。 收藏按钮真正的核心只有 5 行，但 POST 而非 GET、CSRF 凭证、request.user、唯一约束、PRG、相对跳转校验，全是围着这 5 行加的。写代码几分钟，验证和兜底是它的好几倍。

还有判断需求这件事。 从「私聊要像微信那样是独立界面、还要能和不同商品不同买家聊」到「会话顶部要有商品横幅和直接购买」，这些不是语法问题，是把一个模糊的想法拆成表、路由、视图、模板四格的能力。
